# P-01 asyncapi-client.yml 0.2.0 consumes only payment-void-failed: three releaseStock triggers are missing

status: open
found by: zenwave-test-scenarios, claude opus, 2026-11-25
flow: place-order-flow
blocks: releaseStock listeners for PaymentDeclined, PaymentRetryExhausted, PaymentVoided (board S3, S4, S5 tasks marked `blocked: P-01`)

## Problem
releaseStock runs on four payment events
([place-order-flow.zfl:263](../../../arcadia-editions-architecture/business-flows/place-order-flow.zfl#L263)), and the
ZDL declares four listeners
([catalog-inventory-api/domain-model.zdl:174-177](../../../catalog-inventory-api/domain-model.zdl#L174)):
`payment-declined-event-v1`, `payment-retry-exhausted-event-v1`, `payment-voided-event-v1`, `payment-void-failed-event-v1`.
The released [asyncapi-client.yml](../../../catalog-inventory-api/asyncapi-client.yml#L14) (service-all 0.2.0) has only
`payment-void-failed-event-v1` / `onPaymentVoidFailedEventV1`: the repeated `@asyncapi` annotations on one command keep
only the last. The generated SDK has only `IPaymentVoidFailedEventV1ConsumerService`, so no subscription exists for the
other three events, and "the type of the event that triggered this step sets the release reason" can't be honored for
PAYMENT_DECLINED, PAYMENT_RETRY_EXHAUSTED, PAYMENT_VOIDED.

Same pattern in payments-processing-api: voidPayment's two `@asyncapi` lines
([payments-processing-api/domain-model.zdl:190-191](../../../payments-processing-api/domain-model.zdl#L190)) give one
channel in its asyncapi-client.yml.

## Evidence
`target/generated-sources/zenwave/.../asyncapi/client/` contains only `IPaymentVoidFailedEventV1ConsumerService`.
Fixtures C-03/C-07 (PAYMENT_DECLINED), C-08 (PAYMENT_RETRY_EXHAUSTED), C-04/C-09 (PAYMENT_VOIDED) describe states no
listener of this service can produce.

## Options
- A: fix the ZDL-to-AsyncAPI client generation (ZenWave SDK `ZDLToAsyncAPIClientPlugin`) to emit one channel and one
  receive operation per `@asyncapi` annotation; re-release catalog-inventory-api `asyncapi-all` and `service-all` (0.2.1)
  and payments-processing-api the same; bump here and regenerate. Changes: SDK, released contracts; ZDL and fixtures unchanged.
- B: hand-edit catalog-inventory-api `asyncapi-client.yml` to add the three channels/operations and re-release. Changes:
  contract only; drifts from the ZDL on the next generation.
- C: one command per event (`releaseStockOnPaymentDeclined`, ...) each with one `@asyncapi`. Changes: ZDL, generated
  service and tests; duplicates the command.

Recommendation: A, the ZDL already says what is meant; the defect is in contract generation, and payments has it too.
